# Static Build QA — 경계면을 교차 비교한다

## QA의 본체는 존재 확인이 아니다

"파일이 있는가", "함수가 정의되어 있는가"는 검증이 아니다. 각 모듈은 따로 보면 항상 완벽해 보인다. **결함은 경계면에서 나온다** — A가 내보내는 shape과 B가 기대하는 shape이 어긋나는 지점.

그래서 이 스킬의 핵심 동작은 **두 파일을 동시에 열고 비교하는 것**이다. 한쪽만 읽으면 아무것도 발견하지 못한다.

## 원칙: 주장하지 말고 실행한다

"빌드가 통과할 것이다"는 검증이 아니다. `npm run build`를 실제로 돌리고 출력을 인용한다. 실패했으면 실패했다고, 로그와 함께 보고한다. 통과했다고 말하려면 통과한 출력이 있어야 한다.

리포트에 실행 로그를 **요약하지 말고 원문 인용**한다. 요약하는 순간 담당자가 고칠 단서가 사라진다.

## 1. 점진적 QA — 마지막에 몰아서 하지 않는다

팀원이 "모듈 X 완성"이라고 알리면 **그 시점에** X의 경계면을 검증한다.

전체 완성 후 1회로 몰면, 초기 모듈의 결함 하나가 그 위에 쌓인 다섯 개를 함께 무너뜨린다. 그때는 어느 것이 원인인지 가려내는 비용이 결함 자체보다 크다.

## 2. 우선순위 — 위가 실패하면 아래는 볼 필요 없다

### 레벨 1: 빌드 게이트

```bash
npm run build          # = astro check && astro build
ls dist/pagefind/      # 검색 인덱스 생성 확인
node scripts/check-links.mjs   # 깨진 내부 링크 0
```

`astro check`가 실패하면 여기서 멈춘다. 타입이 안 맞는 코드에서 렌더 결과를 검증해도 의미가 없다.

### 레벨 2: 경계면 교차 비교 — QA의 본체

각 항목은 **두 파일을 동시에 읽고** 비교한다.

| 경계면                       | A                       | B                                                 | 확인할 것                                        |
| ---------------------------- | ----------------------- | ------------------------------------------------- | ------------------------------------------------ |
| 스키마 ↔ 콘텐츠             | `content.config.ts`     | 샘플 글 프론트매터                                | 필드명·타입·필수 여부 일치                       |
| 스키마 ↔ 렌더               | Zod 스키마              | 컴포넌트가 읽는 `post.data.*`                     | 컴포넌트가 스키마에 없는 필드를 읽고 있지 않은가 |
| 타입 ↔ props                | 아키텍트 계약 파일      | 컴포넌트 props 실제 사용                          | shape 불일치, 옵셔널 처리 누락                   |
| 설정 ↔ 라우트 ↔ 파일시스템 | `categories.ts`         | `getStaticPaths()`, 내비, `content/posts/` 폴더명 | 4곳의 id 문자열 완전 일치                        |
| 조건부 검증 ↔ 패널          | `superRefine` 강제 필드 | `PaperMetaPanel`/`ProjectMetaPanel`이 읽는 필드   | 패널이 검증되지 않은 필드에 의존하지 않는가      |
| 토큰 ↔ 참조                 | `global.css` 변수명     | 컴포넌트의 `var(--...)`                           | **오타 난 CSS 변수는 조용히 무효화된다**         |
| 모션 ↔ 마크업               | `motion.ts`의 셀렉터    | 컴포넌트의 `data-reveal` 속성                     | 셀렉터가 실제로 잡는 요소가 있는가               |

마지막 두 개가 특히 잘 놓친다. CSS 변수 오타와 셀렉터 불일치는 **에러를 내지 않고 그냥 아무 일도 안 일어난다.**

```bash
# 참조되지만 정의되지 않은 CSS 변수 찾기
grep -rhoE 'var\(--[a-z0-9-]+' src/ | sed 's/var(//' | sort -u > /tmp/used.txt
grep -hoE '^\s*--[a-z0-9-]+' src/styles/global.css | tr -d ' ' | sort -u > /tmp/defined.txt
comm -23 /tmp/used.txt /tmp/defined.txt   # 출력이 있으면 오타이거나 미정의
```

### 레벨 3: CRITICAL 제약

```bash
grep -rn "fetch(" src/                               # 런타임 페치 0건
grep -rnE '#[0-9a-fA-F]{6}' src/components/ src/layouts/   # 색 리터럴 0건
grep -rn "Study Log" src/ --include=*.astro          # 제목 하드코딩 0건 (site.ts 외)
grep -rniE "giscus|comment|댓글" src/                # 댓글 흔적 0건
```

프로필에 창작된 가짜 값이 없는지 `src/config/profile.ts`를 눈으로 확인한다. 플레이스홀더는 **한눈에 플레이스홀더로 보여야** 한다.

### 레벨 4: 접근성 (라이트/다크 양쪽에서)

- 대비 비율 — 계산으로 확인한다. 특히 `#0071e3` on `#000000`(4.47:1, AA 미달)이 어디에도 남아있지 않은지
- 키보드: Tab 순서 = 시각적 순서, 스킵 링크가 첫 포커스 대상, 모바일 시트 포커스 트랩 + Escape + 닫은 뒤 트리거로 포커스 복귀
- 아이콘 전용 버튼 `aria-label` 전수, 장식 아이콘 `aria-hidden="true"`
- 헤딩 위계: 페이지당 `h1` 1개, 레벨 건너뜀 없음
- `prefers-reduced-motion: reduce`에서 모든 모션 정지

### 레벨 5: 반응형 (375 / 768 / 1024 / 1440px)

- **`body` 가로 스크롤 0** — 긴 코드 블록과 넓은 표가 있는 글에서 특히 확인. 이 프로젝트에서 가장 흔한 반응형 사고다
- 터치 타깃 44×44px
- CLS 0

### 레벨 6: 성능

- Lighthouse ≥ 95 (성능·접근성)
- 모션 JS gzip ≤ 12KB — 실측한다:
  ```bash
  find dist/_astro -name "*.js" -exec sh -c 'echo "$(gzip -c "$1" | wc -c)  $1"' _ {} \; | sort -rn | head
  ```
- KaTeX CSS가 `math: true` 글에서만 로드되는지 (약 23KB)
- reduced-motion 환경에서 anime.js가 요청되지 않는지 (Network 탭)

## 3. dev 서버로 검증할 수 없는 것들

**반드시 `npm run build && npm run preview`를 쓴다:**

- Pagefind 검색 — dev에는 인덱스가 없다
- draft 제외 — `import.meta.env.PROD` 분기이므로 dev에서는 draft가 보인다
- 번들 크기 실측
- 최종 링크 경로

dev 서버에서 "검색 잘 되네"는 아무것도 증명하지 않는다.

## 4. 아키텍처 회귀 테스트 — 생략하지 않는다

이 두 시나리오는 편의 기능 테스트가 아니라 **아키텍처 원칙 자체의 회귀 테스트**다.

**시나리오 A — 카테고리 추가**
`categories.ts`에 항목 하나 + `content/posts/<id>/` 폴더 + 글 1편을 추가한다. **다른 파일을 한 줄도 고치지 않고** 빌드해서 새 카테고리 목록·상세·내비 항목이 전부 생기면 통과. 한 줄이라도 고쳐야 하면 실패이고, 그 파일이 파생 체인 밖에 있다는 뜻이다.

**시나리오 B — 스키마 실패**
`category: 'paper-review'`인 글에서 `paper` 블록을 지운다. **빌드가 실패해야** 통과. 경고로 넘어가거나 빌드가 성공하면 실패다 — 그 상태로는 메타 패널이 빈 채로 배포된다.

두 시나리오 모두 검증 후 변경을 되돌린다.

전체 시나리오 10종은 `references/integration-scenarios.md` 참조.

## 5. 결함 리포트 형식

```markdown
| #   | 심각도  | 위치                                 | 증상                                       | 재현            | 담당            |
| --- | ------- | ------------------------------------ | ------------------------------------------ | --------------- | --------------- |
| 1   | BLOCKER | src/pages/[category]/[slug].astro:12 | 빌드 실패: Property 'paper' does not exist | `npm run build` | astro-architect |
```

**심각도:** BLOCKER(빌드/배포 불가) > MAJOR(기능/접근성 결함) > MINOR(개선)

리포트에 반드시 포함할 것:

- **재현 절차** — 없으면 담당자가 고쳤는지 확인할 방법이 없다
- **원인 지목** — "느리다"가 아니라 "KaTeX CSS가 전 페이지에 로드되어 23KB 초과". 원인 없는 리포트는 아무도 못 고친다
- **실행 로그 원문**

## 6. 수정은 담당자에게 넘긴다

결함을 직접 고치지 않는다. 담당 에이전트가 고쳐야 그 사람의 다음 산출물에도 반영된다. QA가 조용히 고치면 같은 결함이 계속 재생산된다.

**예외:** 오타 수준의 명백한 1줄 수정. 이 경우도 고친 뒤 담당자에게 알린다.

**QA가 틀렸을 때:** 담당자가 근거를 들어 반박하면 재검증한다. 잘못된 리포트는 조용히 지우지 말고 철회 사유를 남긴다 — 같은 오판을 반복하지 않기 위해서다.

## 흔한 오탐

| 관찰                      | 결함이 아님                                                                  |
| ------------------------- | ---------------------------------------------------------------------------- |
| dev에서 검색이 안 됨      | 정상. Pagefind 인덱스는 빌드 시 생성                                         |
| dev에서 draft 글이 보임   | 정상. prod에서만 제외                                                        |
| 리빌 애니메이션이 안 보임 | reduced-motion이 켜져 있거나, 화면 밖 요소이거나, `once: true`로 이미 재생됨 |
| 콘솔에 anime.js 요청 없음 | reduced-motion 환경이면 정상 (의도된 게이트)                                 |
